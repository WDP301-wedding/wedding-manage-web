Nguyên tắc vàng khi code FE (đưa nguyên văn cho AI)
1. OpenAPI là luật. Method, path, DTO, field bắt buộc lấy từ openapi.json (digest ở mục 2). Không tự thêm endpoint, không suy quyền từ tên URL.
2. Backend là nguồn sự thật cho tiền, quyền, trạng thái. FE không tự tính tổng tiền, không tự quyết “đã thanh toán”.
3. Không có: RSVP, Household, QR check-in, khách tự đặt tiệc/giữ chỗ, tự đăng ký tài khoản, reset mật khẩu bằng link, hoàn tiền VNPay tự động, xuất XLSX.
4. Mọi lệnh ghi cần Idempotency-Key và thường cần expectedRevision. Gặp 409 → đọc lại dữ liệu mới, không tự “ghi đè”.
5. Thiếu dữ liệu ≠ 0. Check-in tắt hiển thị “Chưa ghi nhận”, không hiển thị 0.

Vì sao Web nên đi qua proxy thay vì gọi thẳng Railway
Cookie làm mới phiên __Host-wedding-refresh có SameSite=Lax: trình duyệt không gửi cookie này khi trang ở localhost:3000 hoặc *.vercel.app gọi fetch sang *.up.railway.app (khác site). Kết quả: đăng nhập được, nhưng sau 10 phút hoặc khi F5 là bị đăng xuất. Ngoài ra backend phải thêm origin của web vào CORS_ALLOWED_ORIGINS.
Cách khuyên dùng: cho Next.js chuyển tiếp (rewrite) /api/v1/* sang backend. Trình duyệt chỉ thấy cùng một origin với trang web, nên cookie được gửi bình thường và không cần CORS. Khi đó đặt NEXT_PUBLIC_API_BASE_URL=http://localhost:3000/api/v1 (local) hoặc https://<domain-vercel>/api/v1 (deploy), còn địa chỉ backend thật để ở biến server BACKEND_ORIGIN (không có tiền tố NEXT_PUBLIC_).
Lưu ý cho BE: qua proxy, mọi request đến từ IP của Vercel → cần xác nhận cấu hình AUTH_TRUST_PROXY_HOPS để giới hạn đăng nhập (10 lần/15 phút) không tính chung cho mọi người dùng.
// next.config.ts – chuyển tiếp API sang backend (áp dụng cho wedding-web và wedding-manage-web)
const backendOrigin = process.env.BACKEND_ORIGIN; // vd. https://wedding-be-production-e1dc.up.railway.app
const nextConfig = {
  async rewrites() {
    return [{ source: '/api/v1/:path*', destination: `${backendOrigin}/api/v1/:path*` }];
  },
};
export default nextConfig;

2.3 Định dạng response và lỗi
Thành công: luôn bọc trong { "data": ... }. Danh sách phân trang có nextCursor (hoặc items + nextCursor).
Lỗi: { "error": { "code": "…", "message": "…", "requestId": "…", "details"?: … } }. Xử lý theo error.code, không dựa vào message (chỉ minh họa). Hiển thị requestId để hỗ trợ tra log.
UUID dạng chữ thường. Thời gian là chuỗi ISO UTC → hiển thị theo giờ Việt Nam Asia/Ho_Chi_Minh. Riêng eventDate (YYYY-MM-DD) là ngày địa phương, không convert múi giờ.
Response private có Cache-Control: no-store → không cache ở client, không dùng SSG cho dữ liệu riêng tư.

2.4 Xác thực (Authentication)
Web (wedding-web, wedding-manage-web)
POST /auth/web-sessions với {email, password} → nhận accessToken (sống 10 phút) và BE đặt cookie __Host-wedding-refresh (HttpOnly, Secure, SameSite=Lax).
Giữ access token trong bộ nhớ (biến/React state), không lưu localStorage. Gửi header Authorization: Bearer <accessToken>.
Hết hạn hoặc reload trang → POST /auth/web-session-refreshes với body {} và credentials: "include" để trình duyệt tự gửi cookie.
Đăng xuất: DELETE /auth/sessions/current. Quản lý phiên: GET /auth/sessions, DELETE /auth/sessions/{sessionId}.
GET /auth/me trả roles (MANAGER, STAFF, COUPLE) → định tuyến theo vai trò.
Nhắc lại: cookie refresh khác site
Cookie __Host- + SameSite=Lax chỉ được gửi khi FE và API cùng site. Nếu FE ở *.vercel.app còn API ở *.up.railway.app thì lệnh refresh sẽ không có cookie → người dùng bị đăng xuất mỗi 10 phút/khi reload.
Cách xử lý: dùng proxy Next.js như mục 2.1. Nếu chạy backend local (localhost:3000 ↔ localhost:3001) thì cùng site nên vẫn chạy được.
Android (wedding-app)
POST /auth/android-sessions → accessToken + refreshToken. Lưu refresh token trong SecureStore, access token trong bộ nhớ.
Làm mới: POST /auth/android-session-refreshes. Refresh token xoay vòng (rotate) – luôn lưu token mới nhận.
Mật khẩu và lời mời
Không có đăng ký công khai. Manager do operator tạo; Staff do Manager cấp; Couple được tạo khi nhận lời mời workspace.
Nhận lời mời: link email chứa token → trang Web gọi POST /workspace-invitation-acceptances {invitationToken, password} → trả luôn phiên đăng nhập. Lời mời sống 72 giờ.
Quên / thiết lập mật khẩu (kể cả Staff mới): POST /auth/password-otp-requests {email} → {challengeId, expiresInSeconds: 600, resendAfterSeconds: 60} → POST /auth/password-otp-completions {challengeId, code, newPassword} → đăng nhập lại.
Đổi mật khẩu khi đã đăng nhập: /auth/password-change-otp-requests → /auth/password-changes.
Mật khẩu 12–128 ký tự. Hai endpoint password-reset-* (link) đã ngừng – code cũ trong repo phải bỏ.
2.5 Idempotency-Key, revision, cursor
Idempotency-Key (1–128 ký tự ASCII in được, nên dùng crypto.randomUUID()): bắt buộc cho hầu hết POST/PATCH/DELETE. Tạo key một lần cho một ý định người dùng (một lần bấm nút). Retry do mất mạng thì gửi lại cùng key và cùng body. Đổi body mà giữ key → 422/409 IDEMPOTENCY_KEY_REUSED.
expectedRevision: chống ghi đè đồng thời (optimistic concurrency). Mỗi tài nguyên có revision riêng – hợp đồng/phụ lục dùng revision của Booking, khách dùng revision của khách, nhóm dùng revision của nhóm… Sau mỗi lệnh ghi, lấy revision mới trong response cho lệnh tiếp theo.
cursor: phân trang dạng con trỏ mờ; khi danh sách thay đổi, cursor cũ có thể báo *_CURSOR_STALE → tải lại từ đầu.
// Gợi ý: wrapper tạo key một lần cho mỗi thao tác
async function runCommand<T>(send: (key: string) => Promise<T>) {
  const key = crypto.randomUUID();        // 1 ý định = 1 key
  try { return await send(key); }
  catch (e) {
    if (isNetworkError(e)) return await send(key); // retry cùng key, cùng body
    throw e;                                       // 409 → reload dữ liệu
  }
}
2.6 Tiền, thời gian, dữ liệu thiếu
Tiền là số nguyên VND (…Vnd). Hiển thị bằng Intl.NumberFormat("vi-VN") + “đ”. Không làm tròn, không tự cộng.
Ca tiệc: LUNCH (Trưa), DINNER (Tối). Giờ ca nằm trong proposal/contract (shiftStartTime, shiftEndTime).
null nghĩa là “chưa có / không đo” – không đổi thành 0. Ví dụ checkedInGuestCount: null → “Chưa ghi nhận”.

5.2 Timeline revision – state
CURRENT (bản đang bàn) → EFFECTIVE (đã được cả Manager và Couple duyệt: mutuallyApproved = true) · bản cũ thành SUPERSEDED. Sửa timeline = tạo revision mới (truyền predecessorRevisionId), mọi duyệt cũ mất hiệu lực. Sau cọc chỉ được đề xuất thay đổi qua change-requests kèm lý do.
5.3 Hợp đồng và phụ lục – state
DRAFT ──submit──▶ AWAITING_APPROVAL ──(Manager + Couple cùng duyệt 1 revision)──▶ APPROVED
  ▲                       │
  └──── withdraw (lý do) ┘   Bản bị thay thế → SUPERSEDED (giữ lịch sử, PDF không đổi)
Sửa nội dung = tạo revision mới (predecessorRevisionId = revision hiện tại), không PATCH.
Hai bên phải duyệt đúng cùng revisionId/documentDigest. Cọc chỉ được khi hợp đồng APPROVED và timeline EFFECTIVE đúng revision mà hợp đồng gắn (timelineRevisionId).
Phụ lục có cùng vòng đời; chỉ sau khi APPROVED mới thay đổi effectiveTotalVnd.

7. Công thức tiền (chỉ để hiểu – FE không tự tính)
lineTotalVnd     = quantity × unitPriceVnd
contractTotalVnd = Σ lineTotalVnd (MENU + PRINT + SERVICE)
depositVnd       = ceil(contractTotalVnd × 30 / 100)
finalTotalVnd    = originalContractTotalVnd + approvedAppendixDeltaVnd
                 + incidentalTotalVnd + invoiceAdjustmentDeltaVnd
netPaidVnd       = settledPaymentsVnd − settledRefundsVnd
balanceVnd       = finalTotalVnd − netPaidVnd
outstandingVnd   = max(balanceVnd, 0)      // còn phải thu
creditVnd        = max(−balanceVnd, 0)     // trả dư
GET /bookings/{id}/billing trả sẵn totals: acceptedChargesVnd, paidVnd, refundedVnd, netPaidVnd, outstandingVnd, creditVnd và history từng bút toán (kind: CHARGE, PAYMENT, REFUND, CREDIT_ADJUSTMENT; sourceType: CONTRACT, CONTRACT_APPENDIX, INCIDENTAL_FINALIZATION, INVOICE_ADJUSTMENT, PRINT_ORDER, PAYMENT_ATTEMPT, …). Số check-in không bao giờ ảnh hưởng tiền.
Ví dụ: hợp đồng 100.000.000đ → cọc 30.000.000đ. Phụ lục +5.000.000đ, phát sinh 2.000.000đ → tổng cuối 107.000.000đ; đã trả 30.000.000đ → còn phải thu 77.000.000đ.

Phụ lục B. Prompt mẫu khi làm việc với AI
Đính kèm tài liệu này (hoặc mục liên quan) và file openapi.json, rồi dùng prompt:
Bạn là frontend developer cho dự án FPT606 (quản lý tiệc cưới, 1 nhà hàng).
Repo: [wedding-web | wedding-manage-web | wedding-app], stack: [Next.js 16 + openapi-fetch | Expo RN].
Nhiệm vụ: làm màn [ID màn hình, vd. C2 – Hợp đồng] cho vai trò [Couple RESTRICTED/FULL | Manager | Staff].
Bắt buộc:
- Chỉ dùng endpoint có trong openapi.json đính kèm; dùng type sinh ở src/lib/api/generated/schema.d.ts.
- Mọi lệnh ghi gửi Idempotency-Key (1 key cho 1 lần bấm) và expectedRevision mới nhất.
- Xử lý lỗi theo error.code; 409 → tải lại dữ liệu; hiển thị requestId.
- Tiền là số nguyên VND do server tính; không tự tính tổng; không báo thanh toán thành công từ redirect.
- Không làm RSVP, Household, QR check-in, đếm người đi kèm, tự đặt tiệc từ catalog.
- Đủ trạng thái: loading, rỗng, lỗi field, lỗi mạng, hết phiên, thiếu quyền, dữ liệu đã đổi, provider chưa sẵn sàng.
- Giao diện tiếng Việt, font sans có dấu, không uppercase; responsive 390px và 1440px.
Trả về: danh sách file thay đổi, code, và giải thích ngắn vì sao chọn cách làm.
